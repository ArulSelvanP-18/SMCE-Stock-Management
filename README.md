# SMCE STOCK MANAGEMENT — Django Web Application

A complete, modular Django rewrite of the SMCE College Stock Management
system (originally specified as a CustomTkinter desktop app). All original
functional requirements are preserved as a multi-user web application backed
by **Supabase (PostgreSQL)**.

## Feature Coverage

- **Login / New Registration** — custom `Member` model (`AbstractUser`) with
  `Role` (Admin/Staff), full name, username, password (hashed), stored in the
  `Member` table.
- **Dashboard** — shows logged-in user's name, live stock counts, and the
  four main sections: MODIFY, VIEW, REPORT, DEAD STOCK.
- **Navigation hierarchy** — Block (Administrative / Eng & Tech 1‑3 / Boys
  Hostel / Girls Hostel / Auditorium) → Department (for Eng & Tech Block 2:
  AI&DS, CSE, ECE, EEE, Civil) → Floor (Underground/Ground/First/Second) →
  Room 1–10 → Room Mini Window → Room Stock Management page. Identical
  structure is reused for both **MODIFY** (editable) and **VIEW**
  (read-only) via a `mode` URL parameter, so there is exactly one
  implementation of the navigation and templates for both.
- **Room Mini Window** — Block Name, Floor, Room Number (auto-filled),
  Room Name, optional Room ID, "auto-update DB" checkbox, OPEN ROOM /
  SAVE CHANGES.
- **Room Stock Management page** — an HTML table (the web equivalent of the
  Treeview) with inline-editable rows. Item Code is read-only and generated by
  the backend from the current Block + Floor + Room + System Control Item Code
  + unique physical-instance suffix. Supports INSERT, UPDATE, DELETE,
  SEARCH (Item Name / Code / No / Room No) with CLICK and SHOW ALL, IMPORT
  CSV/Excel, EXPORT CSV/Excel, SAVE AS CSV, SAVE AS EXCEL.
- **Reports** — filter by Block (or All), Status and complete/partial Item Code,
  with a CLEAR / RESET action. The Item Code search runs across all applicable
  stock records unless a Block filter is explicitly selected.
- **Dead Stock** — filter by source table and search by Item Code or other stock
  fields. A DeadStock row is recorded as a historical snapshot when an item
  becomes Dead; later location/code changes to the live StockItem do not rewrite
  the historical snapshot.
- **Validation** — empty fields, globally duplicate Item Codes, invalid System
  Control mappings, negative quantities, invalid status values, duplicate
  System Control Item Names/codes, duplicate usernames, password
  confirmation, invalid import files, with user-facing messages.
- **Security** — Django's built-in password hashing (PBKDF2), CSRF
  protection, parameterized ORM queries (no raw SQL/SQL injection surface),
  role-based access (`AdminRequiredMixin` / per-view role checks) restricting
  Insert/Update/Delete/Import to Admin users, credentials isolated in `.env`
  (never committed, never hard-coded in source).
- **UI** — Lavender background, Pink titles and buttons, consistent across
  every page, defined once in `static/css/style.css`.

## Design Note: One Stock Table, Not Six

The original desktop spec listed six near-identical stock tables
(`AdministrativeBlock`, `EngandTech1/2/3`, `BoysHostel`, `GirlsHostel`).
Since they share an identical schema, this Django version uses a single
`StockItem` table with a `source_table` field holding the same literal
values (`"AdministrativeBlock"`, `"EngandTech1"`, etc.) — this is exactly
the value the Reports and Dead Stock screens display as `Source_table`.
This avoids duplicate schemas / six-way UNION queries while preserving 100%
of the required per-block behavior, filtering, and reporting.

## Setup Instructions

See **SUPABASE_SETUP.md** for the full, exact walkthrough (creating the
Supabase project, getting the connection string, running migrations). Short
version:

### 1. Create a free Supabase project
Sign up at supabase.com, create a project, and copy the **connection
string** (URI) from Project Settings → Database → Connection string. Use
the "Session pooler" or "Transaction pooler" option, not the direct
`db.<ref>.supabase.co` host.

### 2. Python environment

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### 3. Configure environment variables

```bash
cp .env.example .env
# edit .env: paste your Supabase DATABASE_URL and set a fresh SECRET_KEY
```

Nothing sensitive is hard-coded anywhere in the source; `settings.py` reads
everything from `.env` via `python-decouple`.

### 4. Create tables and seed the navigation catalog

```bash
python manage.py makemigrations
python manage.py migrate
python manage.py initstock --admin-username admin --admin-password "ChangeMe123!" --admin-fullname "System Administrator"
```

`migrate` creates the `Member`, `BlockNode`, `Rooms`, `StockItem`, and
`DeadStock` tables (and all Django auth/session tables) automatically if
they don't exist — equivalent to the original spec's "auto-create database
and tables" requirement. `initstock` seeds the Administrative/Eng&Tech/
Hostel/Auditorium navigation tree and creates your first Admin login.

### 5. Run

```bash
python manage.py runserver
```

Visit `http://127.0.0.1:8000/` — you'll land on the Login page.

## Deploying / Running on Another Machine

Since this is now a web application rather than a desktop `.exe`, deployment
replaces the PyInstaller step:

- **Simplest**: run `python manage.py runserver 0.0.0.0:8000` on the server
  machine and have other machines on the network browse to
  `http://<server-ip>:8000/`.
- **Production**: serve with `gunicorn`/`waitress` behind `nginx` (or a
  managed host such as Render/Railway), run `python manage.py collectstatic`,
  set `DEBUG=False` and a real `ALLOWED_HOSTS` in `.env`, and point
  `DATABASE_URL` at your Supabase project — nothing in the code assumes a
  local database, so the same Supabase project can be reached from any
  server, local machine, or free host.
- No file paths are hard-coded; all static/media paths are relative to
  `BASE_DIR`.

## Roles

- **Admin** — full access: Modify (insert/update/delete/import), View,
  Reports, Dead Stock.
- **Staff** — View, Reports, Dead Stock (read-only); Modify actions are
  blocked with a friendly message and redirect.

## Import File Format (CSV/Excel)

Required columns (case-insensitive, spaces become underscores):
`item_name, quantity, status`

An old file may still contain `item_code` and `item_no`; Item Code is never
trusted from an import. The server resolves the System Control mapping and
generates the current location-based Item Code. `status` accepts `ALIVE`,
`REPAIR` or `DEAD`. Rows are validated before database writes.

The updated project adds:

- Login moved to `/login/`; existing named login/logout/registration links continue to work.
- A `TRANSFER TO →` action on the Modify flow for Admin users.
- A dedicated Transfer Data page with:
  - Source Block → Floor → Room filtering
  - Source room checkboxes (one source room at a time)
  - Record-level checkboxes and Select All
  - Destination Block → Floor → Room filtering
  - Transfer date calendar field
  - Confirmation before moving data
  - Atomic database transfer with duplicate/conflict checks
  - Protection against repeated/double transfers
- A stored DateTime field on `StockItem` and `DeadStock`, displayed as `Insertion/Deletion Date` where required.

### Apply the database upgrade

After replacing the project files, run:

```bash
python manage.py migrate
```

Then start the application normally:

```bash
python manage.py runserver
```

The transfer operation is a MOVE, not a copy: selected records leave the source room and are assigned to the destination room. Existing destination item-code conflicts cancel the entire transfer so partial moves are not created.


## Updated architecture (SMCE Stock Management)
- **PostgreSQL via Supabase** (`django.db.backends.postgresql`) with `psycopg2-binary`, configured through `DATABASE_URL` (via `dj-database-url`).
- Central **SystemItem** master powers System Control, Item Name autocomplete and automatic Item Code selection.
- Stock status values are **ALIVE / REPAIR / DEAD**.
- Quantity-aware, atomic stock transfers with **TransferHistory**.
- Existing stock data is migrated into the SystemItem master by Django migration `0003_system_control_normalize_stock`.
- Stock dates use DateTime fields via migration `0004_datetime_stock_dates`.
- `.env` is intentionally excluded from the distribution. Copy `.env.example` to `.env` and enter your Supabase connection string.

### Local setup
1. Create/activate a Python virtual environment.
2. `pip install -r requirements.txt`
3. Copy `.env.example` to `.env` and set `DATABASE_URL` to your Supabase connection string.
4. Run:
   `python manage.py check`
   `python manage.py makemigrations`
   `python manage.py migrate`
5. Start with `python manage.py runserver`.

The distribution intentionally excludes `.venv`, `venv`, `__pycache__`, `.pyc`, and database credentials. See **SUPABASE_SETUP.md** for the complete step-by-step guide.


## Final System Control / normalization workflow

`SystemItem` is the single central Item Name + Item Code master. Admin users manage it from **SYSTEM CONTROL** on the dashboard. Stock forms use the master relationship and automatically populate the Item Code when an Item Name is selected. The legacy `item_name` and `item_code` columns on `StockItem` are retained only as compatibility mirrors for the existing schema; the `item` ForeignKey is the authoritative relationship.

Item Numbers are generated per master item (for example Laptop 1, 2, 3 and Projector 1, 2, 3) when new stock is inserted. Status is restricted to `ALIVE`, `REPAIR`, and `DEAD`. Repair items are shown on the dashboard and can be opened through the Repair statistic.

Transfers use `transaction.atomic()` and row locks. A partial transfer decreases the source quantity and creates/updates the destination quantity; a full-row move relocates the stock record. Each successful transfer is written to `TransferHistory`.

### Verification note

The distributed source has been statically checked for Python syntax and for MySQL-specific database-driver references (none remain — the ORM usage was already portable). A real `manage.py migrate` against Supabase cannot be executed from this environment without your live Supabase credentials configured in `.env`; the package therefore contains the PostgreSQL configuration and full migration set ready for execution against your Supabase project.


## Item Code Automation (Updated)

Every live `StockItem` now receives a backend-generated, globally unique Item Code:

```text
BLOCK-FLOOR-ROOM-SYSTEM_CONTROL_CODE-INSTANCE
```

Examples:

```text
ADMIN-GF-05-CMP-01
ADMIN-GF-05-CMP-02
ENG-FF-12-PTR-01
```

The System Control Item Code (for example `Computer -> CMP`) is never trusted
from the browser. The backend derives the complete code from the current
`Room`, `SystemItem`, and physical-instance suffix inside a database
transaction. The database also enforces global uniqueness on `StockItem.item_code`.

Moving a stock row regenerates its location portion. Changing a System Control
mapping regenerates current live-stock codes while leaving existing Dead Stock
rows as historical snapshots. Report and Dead Stock pages support dedicated
Item Code searches with partial matching, plus Clear/Reset.

Existing records are upgraded by migration `0005_item_code_automation.py`
without deleting stock data. Legacy import files may still contain an
`item_code` column, but that value is used only to resolve an old System
Control mapping; newly stored stock codes are always generated by the server.

Engineering locations in the existing three-block catalog use the common
`ENG` block prefix, while `source_table` continues to retain the exact
EngandTech1/2/3 identity.
